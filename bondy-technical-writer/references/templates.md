# Document Templates

Skeletons for each document type. Predictable structure is a feature, not a constraint: it lets the
reader learn the shape once and reuse it across the corpus, and it lets you write faster. Adapt the
content; keep the bones.

All templates are Markdown (VitePress/Notion target). Fill bracketed slots; delete guidance notes
(in *italics*) before delivering.

---

## Tutorial

```markdown
# [Build/Write your first <concrete thing>]

*One paragraph: what the reader will have built by the end, and why it's worth their next 20
minutes. Concrete. No theory.*

## Before you start

*The exact prerequisites and environment. Pin versions. If they have these, the tutorial works.*

## Step 1 — [first concrete action]

*Imperative. One action. Show the code/command. Show what they should see as a result.*

> **You should see:** [the observable result]

## Step 2 — [next concrete action]

*...continue. When something needs justification, defer it:*

> We define it this way for now; [why, in the explanation →](link).

## What you built

*Recap the done-state. Confirm the competence the reader just gained.*

## Next steps

*Point to: the explanation that deepens the model, and the how-tos for real tasks.*
```

## How-to guide

```markdown
# How to [accomplish a specific real-world goal]

*One or two sentences: the goal, and who needs it. Assume competence — link theory, don't inline
it.*

**Prerequisites:** [what the reader must already have/know], [link to relevant explanation].

## Steps

1. **[Action].** *The command/code, and the realistic fork if there is one ("if your realm uses X,
   do Y").*
2. **[Action].**
3. **[Action].**

## Result

*Name the done-state: "You now have…". If verification matters, the one check that confirms
success.*

## See also

*The reference for the constructs used; adjacent how-tos.*
```

## Reference page (hand-authored: subsystem / type-form / wire format)

*Use this skeleton only for reference that is **not** a single module's output — a subsystem
spanning several modules, the type-system forms, a wire format. A **module's** reference page is
generated by `bondy docs` from its in-source `@moduledoc`/`@doc`; do not hand-author it — write the
attributes instead (see the in-source skeletons at the foot of this file and
`source-documentation.md`).*

```markdown
# [Construct / subsystem name]

*One-sentence identity. What it is. No teaching — link the explanation that frames it.*

> **Concept:** [Understanding <X> →](link)   ·   **Glossary:** [<term>](link)

## [Task group 1 — e.g. "Creating"]

### `[name/arity or form]`

*Signature / form.*

[Declarative description of what it is.] **Requires** [preconditions]. **Returns/Yields**
[postconditions]. **Effects:** [effects, or "none — pure"]. **Laws:** [@law classifiers and what
they let the reader rely on]. **Fails** [condition → result].

### `[next entry — same skeleton]`

## [Task group 2 — e.g. "Combining"]

### `[name]`

*...same skeleton. Group by task, never alphabetical. The task headings should reveal the shape of
the subsystem's responsibilities.*
```

*Note: every entry of the same kind uses the identical sub-skeleton. The reader learns it once.*

## Explanation

```markdown
# [Understanding <idea> / Why Bondy <does X>]

*Open with the thesis — the one idea this document exists to land. Not "this document covers…";
state the claim.*

## [The problem / the tension]

*What question or difficulty motivates the idea. Ground the reader in why this matters before the
machinery.*

## [The idea]

*Develop the concept. Make connections — to the theory it rests on, to history, to neighbouring
Bondy concepts. Diagrams/examples illustrate; they don't instruct.*

## [Alternatives and trade-offs]

*What else could have been done and why it wasn't. This is the section a sophisticated reader came
for. Be honest about costs.*

## [Consequences]

*What follows for someone using Bondy — what the idea buys them, what it constrains.*

## See also

*The reference for the constructs discussed; the tutorial that exercises them.*
```

## Normative section (specification)

*For a section of a specification. Typst shown, as in the `bondy_lang` book; keep the label on the
heading. Rules in `specifications.md`. Order: definition, normal path, error paths, notes.*

```typst
=== [Section title] <sec-[area]-[topic]>

[Definition. One declarative sentence in the simple present that states what the construct is.
No keyword.]

[Normal path, one requirement per sentence:]
When [trigger], the [conformance target] MUST [response].

While [state], the [conformance target] MUST NOT [response].

[Error paths, one per way a remote party can violate the above:]
If [violation], then the [conformance target] MUST [failure behaviour, naming the error].

[Informative material last, marked as such: an example with fictional identifiers, or a
reference to the rationale by label.]

#warning[
  *Provisional.* [The current leaning, in one sentence.] [Citation of the open question.]
]
```

*Delete the Provisional block unless the section carries an unresolved question.*

## Decision record (BDDR)

*One decision. Rules in `decision-records.md`. Status and date live in the frontmatter only.*

```markdown
---
diataxis: decision
section: bddrs
title: "BDDR-NNNNNN: [The decision as a declarative clause, at most 12 words]"
"@type": "bondy:DesignRecord"
bddr: "BDDR-NNNNNN"
status: Proposed
date: "YYYY-MM-DD"
"bondy:Related":
  - BDDR-NNNNNN
---
# BDDR-NNNNNN: [Same title]

## Decision

[One sentence. Simple present, active voice, named actor. No keyword.]

1. [Optional: at most five clauses, one sentence each, if the decision has parts.]

## Context

*Optional. At most one paragraph: the forces that made a decision necessary.*

## Rationale

- [One reason per item. A claim names its evidence.]

## Alternatives rejected

*Optional.*

- **[Alternative]** — [why it lost, in one or two sentences].

## Consequences

- [What changes for a user or an implementer.]
- [What the decision makes possible, and what it forecloses.]
- [What it costs.]

## Notes

*Optional. "Supersedes BDDR-NNNNNN." Links. A short example.*
```

## Glossary entry

```markdown
**[Term]** — [one-sentence definition, present tense]. *[Optional] Not to be confused with
[neighbour term], which [the distinguishing difference].*
```

*Add an entry whenever you coin or change a Bondy term. The glossary is authoritative: if prose and
glossary disagree, fix one of them.*

## Module doc (`@moduledoc` / `-moduledoc`) — in-source, *this is the module reference*

`bondy docs` renders the module's reference page from this attribute plus the `@doc`/`-doc` on each
public signature. Writing this well **is** writing the reference; there is no separate file. See
`source-documentation.md` for full guidance. Skeleton (Erlang shown; Bondy Lang uses `@moduledoc`):

```erlang
-moduledoc """
[One-sentence identity: what this module is.]

[Two to four sentences of model: the concept the reader needs to make sense of the API, including
the key invariant the module maintains.]

Start from `[entry-point/arity]` and `[entry-point/arity]`.

[Optional one line of rationale, if non-obvious.]
""".
```

## Function doc (`@doc` / `-doc`) — in-source, *rendered into the module reference*

Written on each **public** signature; `bondy docs` renders these as the per-function entries of the
module reference. (Bondy Lang uses `@doc`.)

```erlang
-doc """
[Standalone summary sentence: what it is for, not what it is named.]

[Behavioural contract the -spec cannot state: preconditions, guarantees, effects, determinism,
failure modes, laws. Only the lines that apply.]
""".
-spec name(Arg :: type()) -> type().
```
